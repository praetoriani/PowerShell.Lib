# New-PSModule – Quick Start Guide

## Overview

`New-PSModule.ps1` is a PowerShell utility script that automates the creation of a new module scaffold. In a single run it produces:

- A dedicated **module directory** (`<Target>\<ModuleName>\`)
- A stub **root module file** (`<ModuleName>.psm1`) ready to be filled with your functions
- A fully populated **module manifest** (`<ModuleName>.psd1`) generated by `New-ModuleManifest`

---

## Requirements

| Requirement | Details |
|---|---|
| **PowerShell version** | 5.1 or later (Windows PowerShell or PowerShell 7+) |
| **Execution Policy** | Must allow local script execution – see *Setup* below |
| **Target directory** | Must already exist before running the script |
| **Permissions** | Write access to the target directory |
| **Internet access** | Not required |

## Setup

### 1 – Download the script

Save `New-PSModule.ps1` to any convenient location, e.g.:

```
C:\Scripts\New-PSModule.ps1
```

### 2 – Allow script execution (if not already configured)

Open PowerShell **as Administrator** and run:

```powershell
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
```

> **Why?** By default Windows blocks unsigned scripts. `RemoteSigned` allows locally created scripts to run while still requiring a signature for scripts downloaded from the internet.

## Parameters

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| `ModuleName` | `string` | **Yes** | *(interactive)* | Name of the new module. May use dot-notation for namespacing (e.g. `MyCompany.MyModule`). Each segment must start with a letter and may contain letters, digits, hyphens, or underscores. |
| `ModuleVers` | `string` | No | `1.00.00` | Module version. Accepted formats: `A.BB.CC` or `A.B.C` where each part is a number from 0 to 99 (e.g. `1.00.00`, `2.3.10`). |
| `AuthorName` | `string` | **Yes** | *(interactive)* | Full name of the module author. |
| `Target` | `string` | **Yes** | *(interactive)* | Absolute or relative path to an existing directory that will contain the new module folder. |

## Usage

### Command-line mode (all parameters supplied)

```powershell
.\New-PSModule.ps1 `
    -ModuleName "Contoso.Utilities" `
    -ModuleVers "1.00.00" `
    -AuthorName "Jane Doe" `
    -Target     "C:\Projects\Modules"
```

### Command-line mode (optional parameter omitted – default version used)

```powershell
.\New-PSModule.ps1 `
    -ModuleName "MyModule" `
    -AuthorName "John Smith" `
    -Target     "C:\Modules"
```

### Interactive mode (no parameters supplied)

```powershell
.\New-PSModule.ps1
```

The script will prompt for each required value individually and loop until a valid entry is provided.

### Mixed mode (some parameters supplied, others prompted)

```powershell
.\New-PSModule.ps1 -ModuleName "Contoso.Tools" -Target "D:\Dev"
```

`AuthorName` will be requested interactively; `ModuleVers` defaults to `1.00.00`.

## Output Structure

After a successful run the following files are present on disk:

```
<Target>\
└── <ModuleName>\
    ├── <ModuleName>.psd1    ← Module manifest (auto-generated)
    └── <ModuleName>.psm1    ← Root module stub (ready to edit)
```

### What is in each file?

**`<ModuleName>.psm1`** – A minimal stub with comment-based hints showing how to dot-source public functions and use `Export-ModuleMember`. Fill this file with your module logic.

**`<ModuleName>.psd1`** – A standard PowerShell module manifest containing:
- `ModuleVersion` – the version you specified
- `Author` – the author name you specified
- `GUID` – a freshly generated, unique identifier
- `RootModule` – set to `<ModuleName>.psm1`
- All other fields use the defaults provided by `New-ModuleManifest`

## Validation Rules

The script enforces the following rules and will reject invalid input (either at the command-line or interactively):

| Input | Rule |
|---|---|
| **ModuleName** | Must match `^[A-Za-z][A-Za-z0-9_-]*(\.[A-Za-z][A-Za-z0-9_-]*)*$` – starts with a letter, segments separated by dots |
| **ModuleVers** | Must match `^[0-9]\.[0-9]{1,2}\.[0-9]{1,2}$` – formats `A.B.C` or `A.BB.CC` |
| **AuthorName** | Must not be empty or whitespace |
| **Target** | Must be a non-empty string pointing to an existing directory |

## Error Handling

All file-system operations run inside a `try / catch / finally` block:

- **Errors** are displayed in red with the exception message.
- **Warnings** (e.g. a `.psm1` that already exists) are shown in yellow; the script skips the conflicting step and continues.
- **In all cases** – success or failure – the script ends with `Please press <Enter> to exit ...` so the console window stays visible long enough to read the output.

## Tips & Next Steps

1. **Add the module to your `$PSModulePath`** so PowerShell can find it automatically:
   ```powershell
   $env:PSModulePath += ";C:\Projects\Modules"
   ```
   To make this permanent, add it to your PowerShell profile (`$PROFILE`).

2. **Import and test the module** immediately after creation:
   ```powershell
   Import-Module "C:\Projects\Modules\Contoso.Utilities" -Verbose
   ```

3. **Edit the manifest** with `Update-ModuleManifest` to add descriptions, tags, required modules, and more:
   ```powershell
   Update-ModuleManifest -Path "C:\Projects\Modules\Contoso.Utilities\Contoso.Utilities.psd1" `
       -Description "Utility functions for Contoso environments." `
       -Tags @("Contoso", "Utilities")
   ```

4. **Publish to the PSGallery** (optional):
   ```powershell
   Publish-Module -Name "Contoso.Utilities" -NuGetApiKey "<your-api-key>"
   ```

## Frequently Asked Questions

**Q: The script says "Target directory does not exist" – what do I do?**  
A: Create the directory first (`mkdir C:\Your\Target`) and then re-run the script. The script intentionally does not create the target root to avoid accidental directory creation.

**Q: Can I use a UNC path as the target?**  
A: Yes, as long as the UNC path resolves to an accessible network share with write permissions.

**Q: What happens if the module directory already exists?**  
A: The directory creation uses `-Force`, so an existing folder is left intact. The `.psm1` file is only written if it does not already exist. The manifest is always (re-)generated – this mirrors the behaviour of `New-ModuleManifest`.

**Q: Can I run this from the PowerShell ISE or VS Code?**  
A: Yes. Interactive prompts use `Read-Host`, which works in both environments.

**Q: Is the generated GUID unique every time?**  
A: Yes. The script calls `[guid]::NewGuid()` on each run, guaranteeing a fresh GUID.
